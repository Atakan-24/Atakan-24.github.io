Team Gold — Cold-Calling CRM & AI Voice Platform

Sole builder & operator

A Next.js CRM built for a real cold-calling sales team: browser-based softphone dialing over WebRTC/Telnyx, an outbound AI voice agent that can run its own call shifts, live call recording and two-channel transcription, and a lead-scoring engine that decides who gets called next.

100k+leads scored & routed
7rotating outbound numbers, load-balanced
14+iterated call-script versions, A/B tested
What made this hard
  • Trustworthy scoring, not a vanity number. Lead priority combines need, budget, and reachability with a geometric mean instead of a raw product — a raw product looked fine in a spreadsheet but pushed almost the entire dataset into a handful of duplicate scores, which silently destroyed the ranking the dialer relied on.
  • Call outcomes you can actually trust. Rep- entered call results turned out to be unreliable at scale, so every claimed outcome is now cross-checked against the one number a rep can't fake: measured call duration from the telephony provider itself.
  • Two-channel audio, correctly attributed. AI call review needs to know who said what. Recordings are split into separate agent/customer channels before transcription — naive single-channel transcription let the model guess the speaker from content alone, which was wrong far more often than it looked.
  • An AI agent with a hard leash. The outbound voice agent has its own budget cap, a compliance-driven call-window check, and a kill switch that a plain config change can't accidentally re-enable — the safety property that matters here is that "off" always means off, not "off unless five different code paths all agree."

Lead Generation Pipeline — Google Maps at Scale

Sole builder & operator

A always-on scraping and enrichment pipeline that finds local businesses, checks whether they still exist, reads their websites for real signals (hiring activity, ad spend, tech stack), and turns all of that into a single, explainable priority score — running continuously, watched by its own health checks.

24/7self-healing background process
2independent scrapers, cross-verified
30+extracted business signals per lead
What made this hard
  • "Still running" isn't a status you can assume. A crashed browser sub-process looked identical to a healthy one in the process list. The watchdog now checks actual CPU activity over a time window, not just whether the PID exists — the difference between those two once cost three days of silent downtime.
  • Pagination under concurrent writes is a trap. Paging through a database with plain offsets while the table is being written to at the same time silently duplicates and skips rows — invisible until someone compares two "complete" scans and gets two different totals. Every long-running scan here pages by a stable cursor instead.
  • A null is not a zero. "Never measured" and "measured and it's zero" look the same in a spreadsheet but mean opposite things for a scoring model — conflating them once quietly threw out a third of a live dataset's worth of good signal.

AI-OS — A Multi-Agent Operations Layer for a Real Business

Sole builder & operator

Instead of a single AI assistant, this is an operating layer: a library of reusable agent "skills," a policy that routes each task to the right model and effort level, scheduled autonomous work, and a Telegram-based approval channel so a human makes the handful of decisions that actually matter — money, access, and direction — while everything routine runs unattended.

20+purpose-built agent skills
8tiered escalation signals for model routing
24/7daemon with human-in-the-loop approval gates
What made this hard
  • Autonomy needs a real off switch, not just a polite one. Every action with a cost — a paid API call, an outbound message, a purchase — routes through an explicit money/access/direction gate that pauses the agent and asks a human via a structured, button-based approval flow, not free text to a shell.
  • "It ran" isn't "it worked." A background daemon can die silently for days while every scheduled job still shows as configured. The fix wasn't a bigger try/catch — it was a separate watchdog that checks the checker.
  • Model routing as policy, not vibes. Which model and how much reasoning effort a task gets is decided by an explicit, versioned scoring policy across eight dimensions (ambiguity, blast radius, architectural weight, and so on) — not re-guessed every time from scratch.

teamgoldllc.de — Bilingual Marketing Site & SEO Engineering

Built & shipped

The public site for the business the systems above serve. A React single-page app in two languages, with the structured-data and loading work that decides whether a small business is findable at all — the part of "a website" that is engineering rather than decoration.

2languages, full translations
4JSON-LD schema types
liveat teamgoldllc.de
What made this hard
  • Two languages, not a language switcher. Full EN and DE translation files with correct hreflang including x-default — which is what stops Google serving the German page to a US searcher and treating the pair as duplicate content.
  • Structured data as a first-class output. Four JSON-LD types (WebSite, Organization, Service and an OfferCatalog of the individual services). Search engines can read what the business sells without parsing the prose — which is the entire point of doing SEO as markup rather than keyword stuffing.
  • Fonts that do not block the first paint. Preloaded as a stylesheet with an onload swap and a <noscript> fallback, plus a preconnect for the booking widget. Every one of these is verifiable in the page source — which is exactly where a technical reviewer will look.

Honest scope: this was assembled fast on React with a component library, not hand-written from zero. What I own here are the decisions — the bilingual structure, the schema modelling, and the loading strategy.

Code

Three real patterns from the systems above (renamed, generalized — no business data), and one small tool you can actually run.

scoring.ts
// Priority score: geometric mean, not a raw product.
// A raw product crushed almost the whole dataset toward zero;
// reachability acts as a multiplier band, not a third equal factor.
const core   = Math.sqrt((need / 100) * (budget / 100));
const factor = 0.5 + (reachability / 100) * 0.8;
const priority = Math.min(1000, 1000 * core * factor);

Fixed a bug where thousands of leads landed on the exact same score — the dialer's "best next call" was silently random.

paginate.ts
// Offset pagination breaks under concurrent writes: rows get
// skipped or duplicated mid-scan. A cursor doesn't care what
// happened before it — it only knows the last id it saw.
let lastId = 0;
while (true) {
  const rows = await db.query(
    `select * from contacts where id > $1 order by id asc limit $2`,
    [lastId, PAGE_SIZE]
  );
  if (rows.length === 0) break;
  process(rows);
  lastId = rows[rows.length - 1].id;
}

Two "complete" scans of the same table were quietly returning different totals until this replaced a plain offset loop.

safety-lock.ts
// "Off" always means off — not "off unless five different
// code paths all happen to agree." Every response is rewritten
// through one choke point before it's ever sent.
function sendInboundResponse(xml: string): string {
  if (INBOUND_AI_LOCKED && containsAiAssistant(xml)) {
    return VOICEMAIL_FALLBACK_XML; // hard override, not a suggestion
  }
  return xml;
}

The safety property lives in code, at a single choke point — not spread across a dashboard toggle, a database row, and a config flag that all have to agree.

git-secret-scan

A dependency-free pre-commit hook and GitHub Action that stops API keys from reaching a commit — written after a real incident where five live credentials sat exposed in a repo for months, unnoticed until a backup was being prepared.

The part worth reading: I measured it and found it broken

The tool had never been measured. Building a labelled corpus of 61 cases surfaced three bugs, all false negatives — the failure mode that matters in security work, because it looks exactly like success.

  • The false-positive guard was eating real tokens. It demanded an uppercase letter and a digit in every match. Slack and GitHub tokens are routinely lowercase-plus-digits, so 2 of 10 credential types were undetectable. Worse, it no longer did the job it was written for — the patterns had since gained a word boundary that handled that case anyway.
  • A placeholder anywhere on the line disabled the line. A real key with // see EXAMPLE in a trailing comment went through silently.
  • A broken git environment reported "clean". Run outside a repository it printed clean and exited 0. A hook that passes when it cannot see anything is worse than no hook, because it is trusted.

Recall went from 80 % to 100 %, precision from 91.4 % to 100 %, measured — and the benchmark now gates CI, so a regression fails the build instead of going unnoticed.

Two more things only real delivery teaches: GitHub's own push protection blocked the first push, because its scanner could not tell my synthetic test token from a live one — fixed by assembling fixtures from parts rather than weakening the check. And the CI matrix caught a genuine Python 3.9 incompatibility that a machine running 3.12 could never have surfaced.
